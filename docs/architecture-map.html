1 · Components and the hub boundary

What runs where, and how the pieces talk

Apps on one hub cannot safely call each other, except a parent calling its own children (two single-threaded apps calling each other can deadlock). So the Engine calls its rule containers directly, and everything else travels as location events, files in File Manager, or loopback HTTP. Each numbered line is explained under the diagram.

2 · Data flows

Five sequences, step by step

Each step names the file or function that does it.

a

Author a rule

  1. Open. editorPageGet serves hai-editor.html from File Manager after the EDITOR_PAGE_SHA256 check. The page fetches /editor/api/fixed (cached per build) and /editor/api/state.
  2. Edit. Forms come from the field specs; each block shows the hub's own sentence from hai_render. /editor/api/device reads one named device.
  3. Check. POST /editor/api/check: hai_editor validates (hai_validator), simulates (hai_sim) and renders, reading only that rule's devices. Returns findings and a receipt, an HMAC with haiReceiptKey.
  4. Save draft. POST /editor/api/save or /draft into the filed store (editorDrafts): 64 KB a draft, 384 KB in all. The running rule is untouched.
  5. Put on hub. POST /editor/api/send: a valid receipt skips re-checking; editorSubmission signs with haiSigningKey; runtimeSubmitBody hands it to the runtime in the same request.
  6. Review. rtCheckSubmission (signature, age under two minutes, not one of the last 16), then rtReview (validate, allow-list, driver commands, node count).
  7. Deploy to the container. haiSetup and haiStage (rtStage), then haiCommit runs rtCommit: hash matches, devices allowed, subscribe, arm schedules. The rule app sends haiRuleCommitted; the registry marks it active. An unconfirmed stage is reconciled 15 s later (haiReconcileSoon).
b

An event fires a rule

  1. Delivery. Hubitat calls haiEvent, haiMode, haiVariable or haiTimer in hai_rule_app.groovy, which calls rtOnEvents.
  2. Begin. rtExecute wraps the execution; rtBegin loads state.rt once, runs rtBoot (restart?) and rtSettleFences.
  3. Admit. coreAdmit: trigger match, required expression, rerun policy; at most 1024 evaluations per event (RT_MAX_EVALS_PER_EVENT).
  4. Gate. coreGate reads conditions in three-valued logic (hai_logic); unknown with onUnknown: block stops the run with its reason.
  5. Actions. coreExecute runs the steps. A send passes the allow-list (rtChildAllowed), the driver check and a fence, then climbs requested, dispatched, confirmed. Waits become rows in rt.deadlines with a runOnce wake-up.
  6. History. rtEnd compacts the trace (rtCompact), applies the byte budget (rtBudget), decides rtSelfCheckWanted, saves the light mark (rtLight) and writes state.rt once. hai_timeline answers "why did this run".
  7. Self-check. One runOnce of haiSelfCheck at the earliest unfired dueAt; nothing is scheduled when nothing is pending.
  8. Watchdog. haiWatchdog every 15 minutes calls each active rule's haiOverdue: fires anything 30 s past due, reports health, returns the light mark. The quiet path (rtOverdueQuiet) writes nothing when all is well.
c

Migration: scan, decode, assess, clone, test, cutover, rollback

optional
  1. Scan. AM /scan (or the daily scheduledScanHandler, off by default): fetchRegistry reads /hub2/appsList, then statusJson per app, decoders per engine (SUPPORTED_RULE_ENGINE = 'Rule-5.1'), buildGraph, finishScan.
  2. Decode. finishScan writes ham-decode(-dev).json (ham.decode/1) and ham-decode-detail(-dev).json (ham.decode.detail/1) inside hamDecodeEnvelope: contractSchemaVersion 4, fails closed.
  3. Read. GET /migration/api/state: Migration reads the decode (hai_ham, refusing a schema not in HAM_SCHEMAS) and asks haiMigrationFacts for HAI's rules and the ledger.
  4. Assess. Each rule gets ready, needs-decision, partial or blocked, with unmapped constructs and coupling (rmCoupling). Assess now: POST /migration/api/assess sends haiAssessRequest; AM's haiAssessRequestHandler rescans the named rules (a full scan above 40 percent, HAI_ASSESS_FULL_SCAN_SHARE) and answers haiAssessDone.
  5. Clone, stopped. POST /migration/api/apply op=clone: rmRebuild then rmFaithful; haiMigrationCall('importRule') creates a disabled HAI rule; haiMigrationRecord sets phase: cloned with rmPrint. Bulk copies take up to 6 (MIG_BATCH_MAX) and no upgrades.
  6. Test. The copy stays disabled while it is tried: a dry run through the Engine's simulator (/migration/api/dryrun), Run now or Run one step in the editor (/editor/api/run-step), and the rule harness, which compares it with the Rule Machine original.
  7. Cutover. op=switchOver: RMUtils pauseRule, read back three times 250 ms apart, then activateStopped and phase: switched. The Engine announces haiRmSwitched so callers retarget.
  8. Watch. Each switched copy's last run, a run that went wrong, and "changed since copied" when the Rule Machine fingerprint no longer matches rmPrint.
  9. Rollback. op=switchBack: haiRuleOp stops the copy, RMUtils resumeRule, read back, phase: reverted. Deleting the HAI copy (deleteClone) is a separate deliberate act; nothing deletes automatically.

Two engines running one rule is the worst outcome, so the pause read-back before activation is never skipped. Rule Machine is never parsed by HAI: AM owns the storage format, HAI owns the translation.

d

The capability feed into AM's coverage table

  1. Source. The parity tracker, generated into engine/app/am/capabilities.json (ids in capability_ids.json).
  2. On the hub. upload-editor-page.ps1 uploads it as hai-am-capabilities.json; the Engine embeds its hash (AM_CAPS_SHA256) and refuses a copy that differs.
  3. State file. On each announce the Engine's haiWriteAmStateNow writes hai-am-state.json (hai.am/1 shape from hai_am: rules as nodes, edges, flows) with capabilitiesHash, not the 50 KB list.
  4. Local read. AM reads /local/hai-am-state.json over loopback, draws HAI rules on the map, and re-reads /local/hai-am-capabilities.json only when the hash moves.
  5. No local Engine. AM fetches public/hai-capabilities.json from Automation Map's public repository on GitHub (HAI_PUBLIC_CAPABILITIES_URL), made by the public-list scripts.
  6. Table. AM renders Table 1 (HAI's Rule Machine coverage). Table 2 (/rm-coverage) is separate: what the user's own rules need.
  7. Guard. FEED_LOCK.json pins the SHA-256 of every piece, and CI checks the pins on every push. A change to the feed is a deliberate re-pin.
e

MCP propose, human approve

  1. Connect. The client calls POST /mcp with the token and the mcp audience secret (MCP protocol 2024-11-05, 2025-03-26, 2025-06-18).
  2. Learn. hai_describe returns the rule format guide (hai-author-guide.txt, hash-checked), the command catalogue and the inventory.
  3. Propose. hai_propose_rule: hai_propose checks, reads back and simulates, and stores a proposal (filed proposals). It never activates, commands or deletes.
  4. Review. A person opens it in the editor and reads the hub's rendering (hai_render), the structural diff and the findings, never the model's own words.
  5. Approve. The person presses Check, then Put on hub: steps 3 to 7 of flow (a). The in-editor AI author (authorStart, authorOnResponse) ends the same way: always a draft.

The mcp audience is what stops an MCP client calling /editor/api/send; the tool list alone is not a boundary.

5 · Trust boundaries

Tokens, guarded calls, and the human decision

A person approves before anything is deployed

The AI author and MCP clients only produce drafts and proposals. Put on hub, pressed by a person in the editor, is the decision, and it goes through the same Check and activation review as any rule. Migration's Copy makes a disabled rule; Switch over is a separate press.

OAuth token per app

Engine, Migration and Automation Map each have one access token that reaches all of that app's paths. Migration's token reaches nothing else.

Route audiences

The Engine's HAI_ROUTE_AUDIENCE: feed (open, read-only), mcp, editor, endpoint. A wrong aud gets 403 WRONG_AUDIENCE.

Approved devices

The one permission. rtReview refuses a device or command outside it; rtChildAllowed re-checks before every send.

Signed submission

haiSigningKey; rtCheckSubmission checks the signature, age under two minutes and no replay (last 16 kept). haiRuleSubmit events are checked the same way.

Receipts and claims

Check receipts are HMACs with haiReceiptKey, which never leaves the hub. Activation uses single-use claim ids with nonces and expiry.

Page integrity

Each app embeds the SHA-256 of its pages (//#sha256 from assemble.py) and refuses to serve a File Manager copy that differs.

HTTP steps

Any host may be reached; a built address may not reach the hub's admin API. A literally written address is allowed.

Other apps' requests

haiRuleApi requests must carry the Engine's API token; without it there is no reply. Change HAI's access addresses replaces the OAuth token, audience secrets and API token in one press.

Open: Assess now events

haiAssessRequest is an unauthenticated hub-local event. The signing and receipt keys are not rotated.

Hub data

Automation Map's repository is public and carries no hub data. Examples use invented names such as Hall Light.
